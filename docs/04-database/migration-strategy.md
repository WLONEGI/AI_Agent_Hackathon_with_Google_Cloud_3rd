# データベースマイグレーション戦略

> **TL;DR**: バージョン管理統合のスキーマ変更管理戦略。7段階マイグレーションファイル体系（初期スキーマ→クォータ→パーティション→インデックス→監査→プレビュー→パフォーマンス）、環境別段階的デプロイ（dev自動・staging手動承認・prod計画実行）、安全なロールバック機能、データライフサイクル管理（無料30日・有料1年保持）で構成。GitHub Actions自動化、日次クリーンアップ（3時UTC）、週次VACUUM（日曜4時UTC）、バッチ処理による大量データ移行、CONCURRENTLY活用のオンラインインデックス作成。

## 🔄 マイグレーション戦略

### スキーマ変更管理方針
- **バージョン管理システムとの統合**: 変更履歴の一元管理による透明性確保
- **環境別の段階的デプロイ**: リスク最小化とテスト体系
- **本番環境での変更窓口**: 承認プロセスによる品質保証

### マイグレーション実行戦略
- **開発環境**: 自動実行による開発効率化
- **ステージング環境**: 手動承認による品質保証
- **本番環境**: 計画的実行とダウンタイム最小化

## 🔙 ロールバック戦略

### 安全なロールバック方針
- **マイグレーション履歴の追跡**: すべての変更を記録・追跡可能
- **段階的なロールバック**: ステップバイステップでの安全な復元
- **データ整合性確認**: ロールバック後の状態検証
- **スキーマオブジェクト検証**: インデックス、ルール、トリガーの状態確認

### ロールバック実行要件

```yaml
ロールバック手順設計:
  ステップ1_現在状態確認:
    目的: 現在のスキーマバージョン特定
    取得情報:
      - 最新マイグレーションバージョン
      - 適用済みマイグレーション一覧
      - スキーマオブジェクト一覧
    実装要件:
      - schema_migrationsテーブル照会
      - ORDER BY version DESC LIMIT 1で最新取得

  ステップ2_ロールバック対象確認:
    目的: 戻すべきマイグレーションの特定
    確認項目:
      - 対象バージョン範囲
      - 依存関係の逆算
      - データ影響範囲
    実装要件:
      - WHERE version > 'target_version'で対象抽出

  ステップ3_段階的ロールバック実行:
    実行方針: 各マイグレーションのdown処理を逆順実行
    実行単位: 1ファイルずつ
    検証: 各ステップ後の整合性確認

  ステップ4_整合性確認:
    検証項目:
      - テーブル構造の正確性
      - 制約の有効性
      - インデックスの存在
      - データ参照整合性
      - トリガー・ルールの状態

整合性確認要件:
  テーブル構造検証:
    確認対象: information_schema.tables
    検証内容: 期待されるテーブル構造との一致
    実装要件:
      - table_name, column_name, data_typeを照会

  制約検証:
    確認対象: information_schema.table_constraints
    検証内容: 主キー、外部キー、CHECK制約の有効性
    実装要件:
      - constraint_name, constraint_typeを照会

  インデックス検証:
    確認対象: pg_indexes
    検証内容: 期待されるインデックスの存在と有効性
    実装要件:
      - indexname, indexdefを照会して確認
```

## 📊 データライフサイクル管理

### 期限切れデータの削除戦略

```yaml
無料ユーザーデータ削除設計:
  保持期間: 30日
  削除対象:
    テーブル: manga_projects
    条件:
      - expires_at < 現在時刻
      - account_type = 'free'

  削除処理要件:
    処理方式: バッチ削除
    削除クエリ:
      対象テーブル: manga_projects
      WHERE条件: expires_at < NOW() AND user_id IN (SELECT user_id FROM users WHERE account_type = 'free')
    バッチサイズ: 1,000件/回
    実行タイミング: 毎日3時UTC
    エラーハンドリング: ログ記録＋リトライ

有料ユーザーデータ削除設計:
  保持期間: 1年
  削除対象:
    テーブル: manga_projects
    条件:
      - expires_at < 現在時刻
      - account_type = 'premium'

  削除処理要件:
    処理方式: バッチ削除
    バッチサイズ: 500件/回
    実行タイミング: 毎日3時UTC
    通知: 削除30日前にメール通知

データ削除実行計画:
  スケジュール:
    頻度: 毎日
    実行時刻: 3時UTC（日本時間12時）
    理由: システム負荷が最小の時間帯

  処理方式:
    アプローチ: バッチ処理
    バッチサイズ: アカウント種別により可変
    トランザクション: バッチ単位でコミット

  監視要件:
    記録項目:
      - 削除件数（無料/有料別）
      - 処理時間
      - エラー発生件数
      - 影響行数

    アラート条件:
      - 削除件数が前日比200%超
      - エラー率が5%超
      - 処理時間が10分超
```

## 📈 パフォーマンス考慮事項

### 大量データマイグレーション設計

```yaml
バッチ処理要件:
  処理方式: ページネーション方式
  バッチサイズ: 10,000件/回
  コミット頻度: バッチ単位

  処理フロー設計:
    変数定義:
      - batch_size: INTEGER型（10,000）
      - total_count: INTEGER型（総件数）
      - processed: INTEGER型（処理済み件数、初期値0）

    ステップ1_総件数取得:
      処理: source_tableの総件数をCOUNTでtotal_countへ格納

    ステップ2_ループ処理:
      条件: processed < total_count
      処理内容:
        a. source_tableからLIMIT batch_size OFFSET processedでデータ取得
        b. target_tableへINSERT
        c. processedをbatch_size分増加
        d. COMMIT実行
        e. 進捗ログ出力: 'Processed: {processed}/{total_count}'
      繰り返し: ステップ2をループ

  進捗監視:
    ログ出力頻度: バッチ処理ごと
    ログ内容: "Processed: {処理済み件数}/{総件数}"
    推定残り時間: 算出して表示
    実装要件: RAISE NOTICE使用

  エラーハンドリング:
    失敗時の動作: 当該バッチのみロールバック
    リトライ: 3回まで自動リトライ
    最終失敗時: エラーログ記録＋処理停止

パフォーマンス要件:
  処理速度目標: 10,000件/秒
  メモリ使用量: バッチサイズに応じて調整
  CPU使用率: 70%以下を維持

  並列処理:
    条件: 100万件以上のデータ移行時
    並列度: 4並列まで
    パーティション単位: テーブルパーティション別
```

### インデックス再構築戦略

```yaml
オンライン再構築要件:
  使用オプション: CONCURRENTLY
  目的: サービス停止なしでのインデックス作成
  制約:
    - トランザクション内での実行不可
    - 通常より時間がかかる
    - ディスク容量が一時的に増加

  適用条件:
    - 本番環境での全インデックス作成
    - ステージング環境（推奨）
    - 開発環境（任意）

段階的実行戦略:
  実行タイミング:
    本番環境: 深夜帯（2-5時UTC）
    ステージング環境: 営業時間外
    開発環境: 任意

  実行順序:
    優先度高: 頻繁に使用されるインデックス
    優先度中: 定期的に使用されるインデックス
    優先度低: 稀に使用されるインデックス

  インターバル:
    各インデックス作成間隔: 5分
    理由: システム負荷の分散

監視要件:
  監視項目:
    - インデックス作成進捗
    - CPU使用率
    - ディスクI/O
    - ディスク空き容量
    - ロック待機状況

  アラート条件:
    - CPU使用率90%超
    - ディスク空き容量10%未満
    - ロック待機5分超

  対応:
    - 高負荷時は一時停止
    - ディスク不足時は処理中断
    - ロック競合時は再スケジュール
```

## 🔍 マイグレーション検証

### 検証項目チェックリスト

```yaml
スキーマ検証:
  □ スキーマバージョンの一致確認
    確認方法: schema_migrationsテーブル照会
    期待値: 最新バージョンと一致

  □ テーブル構造の整合性確認
    確認方法: information_schema.tablesとの比較
    期待値: 設計書通りのテーブル構造

  □ インデックスの存在確認
    確認方法: pg_indexesビュー照会
    期待値: 設計書に記載の全インデックスが存在

  □ 制約の有効性確認
    確認方法: information_schema.table_constraints照会
    期待値: 全制約が有効状態

  □ データ型の一致確認
    確認方法: information_schema.columns照会
    期待値: 設計書通りのデータ型

  □ 権限設定の確認
    確認方法: pg_rolesおよびACL確認
    期待値: ロール別の適切な権限設定

  □ パフォーマンステスト実行
    確認方法: 主要クエリの実行計画確認
    期待値: インデックスが適切に使用される

データ整合性検証:
  □ 外部キー制約の整合性
    確認方法: 孤立レコードの検索
    期待値: 孤立レコード0件

  □ NOT NULL制約の確認
    確認方法: NULL値の存在チェック
    期待値: NOT NULLカラムにNULL値なし

  □ UNIQUE制約の確認
    確認方法: 重複値の検索
    期待値: UNIQUE指定カラムに重複なし
```

### 自動テスト体系設計

```yaml
スキーマ整合性テスト設計:
  テスト名: test_schema_integrity
  テスト種別: 構造検証
  実行タイミング: マイグレーション直後
  戻り値: boolean型

  テスト項目:
    テーブル存在確認:
      対象: 全テーブル（例: users）
      検証内容: information_schema.tablesに存在
      実装要件:
        - SELECT 1 FROM information_schema.tables WHERE table_name = 'テーブル名'で存在確認
        - 存在しない場合はRAISE EXCEPTION
      エラー処理: 'Table {テーブル名} does not exist'例外発行

    インデックス存在確認:
      対象: 全インデックス（例: idx_users_email）
      検証内容: pg_indexesに存在
      実装要件:
        - SELECT 1 FROM pg_indexes WHERE indexname = 'インデックス名'で存在確認
        - 存在しない場合はRAISE EXCEPTION
      エラー処理: 'Index {インデックス名} does not exist'例外発行

    最終結果: 全チェック成功でtrue返却

パフォーマンステスト設計:
  テスト名: test_query_performance
  テスト種別: パフォーマンス検証
  実行タイミング: マイグレーション完了後

  テスト項目:
    主要クエリ実行計画:
      対象クエリ: 頻出クエリTop 10
      検証内容: インデックス使用の確認
      期待値: Index Scan使用
      実装要件: EXPLAIN ANALYZEで実行計画取得

    実行時間計測:
      対象クエリ: 全主要クエリ
      検証内容: 実行時間がしきい値以下
      しきい値:
        - 単純SELECT: 50ms以下
        - JOIN含むSELECT: 200ms以下
        - 集計クエリ: 500ms以下
      実装要件: pg_stat_statementsまたはタイムスタンプ差分で計測

ロールバックテスト設計:
  テスト名: test_rollback_integrity
  テスト種別: ロールバック検証
  実行タイミング: ステージング環境で定期実行

  テスト項目:
    ロールバック実行:
      手順: マイグレーション実行 → ロールバック
      検証内容: 元の状態に完全復元

    データ損失確認:
      手順: ロールバック前後のデータ比較
      検証内容: データ件数・内容の一致
      実装要件: COUNT(*)比較、CHECKSUM比較

    スキーマ復元確認:
      手順: ロールバック後のスキーマ検証
      検証内容: ロールバック前のスキーマと一致
      実装要件: information_schemaの各ビューで比較
```
